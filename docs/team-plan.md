# 兩人團隊詳細分工計畫

團隊：隊長林芝瑩 + 組員 1 位，共 2 人。決賽 2026/9/12-13，30 小時內交件。

---

## 一、分工總原則

1. **兩條垂直線平行開發**：隊長顧「資料→分數」，組員顧「分數→畫面」。
2. **介面先行**：中間用一份 `data/processed/kindergartens.csv` 當交接契約。欄位先講好，隊長先給「假資料版」，組員立刻能開工，不用等真資料。
3. **每 6 小時對一次**：確認 CSV 欄位一致、Demo 流程能串起來。
4. **AWS 部署放最後**：先在本機把功能跑出來（localhost 也能 Demo），最後 6 小時再上雲。這段主要由隊長最後處理（你說最後再用）。

## 二、交接契約：kindergartens.csv（最重要，先定好）

這是兩人之間唯一的介面。欄位定義：

| 欄位 | 說明 | 誰產出 | 誰使用 |
|------|------|--------|--------|
| `park_id` | 園所編號 | 隊長 | 兩人 |
| `park_name` | 園所名稱 | 隊長 | 組員(顯示) |
| `park_type` | 公校/非營利 | 隊長 | 組員(篩選) |
| `year` | 年度 | 隊長 | 兩人 |
| `address` | 地址 | 隊長 | 組員(地圖) |
| `lat` / `lng` | 緯度/經度 | 隊長(geocoding) | 組員(地圖標點) |
| `cost_per_child` | 每幼兒單位成本 | 隊長 | 組員(明細) |
| `personnel_ratio` | 人事費占比 | 隊長 | 組員(明細) |
| `income_expense_ratio` | 收支比 | 隊長 | 組員(明細) |
| `benford_mad` | 班佛偏離度(MAD) | 隊長 | 組員(明細) |
| `yoy_change` | 跨年度變動幅度 | 隊長 | 組員(明細) |
| `penalty_count` | 裁罰次數 | 隊長 | 組員(明細) |
| `eval_grade` | 評鑑等第 | 隊長 | 組員(明細) |
| `score_financial` | 財務異常分項分 | 隊長 | 組員(雷達圖) |
| `score_penalty` | 裁罰分項分 | 隊長 | 組員(雷達圖) |
| `score_eval` | 評鑑分項分 | 隊長 | 組員(雷達圖) |
| `score_sentiment` | 輿情分項分 | 隊長 | 組員(雷達圖) |
| `risk_total` | 總風險分(0-100) | 隊長 | 組員(排名/地圖顏色) |
| `risk_level` | 高/中/低 | 隊長 | 組員(紅黃綠) |
| `ai_report` | AI稽查建議(文字) | 組員(Bedrock) | 組員(明細顯示) |

**動作**：兩人第一件事就是一起把這張表確認好，隊長馬上產一份 15-20 列的假資料 CSV 丟給組員。

## 三、隊長林芝瑩 — 「資料與風險引擎」線

你是專業度核心，負責從原始 PDF 到風險分數。

### 模組 L1：財務資料抽取
- 從公校決算書第5冊抽各市立幼兒園財務數字（pdfplumber）
- 抽：收入、支出、人事費、業務費、幼兒人數、各年度數字
- 產出：`data/processed/financials.csv`（原始數字）
- 卡住備案：若某園版面難解析，先手動補該園數字，先求15間能跑

### 模組 L2：鑑識會計三招（你的護城河）
- **班佛定律**：取每園所有財務數字的首位數，算分布與理論值的偏離度(MAD)，MAD越大越可疑
- **財務比率勾稽**：每幼兒單位成本、人事費占比、收支比，找離群值(用中位數±倍數或分位數)
- **跨年度趨勢突變**：同園跨年度費用/收入變動幅度，暴增暴減標記
- 產出：每園每項指標 + 是否異常旗標

### 模組 L3：可解釋風險評分模型（白盒子）
- 四個分項各給分：財務異常、裁罰、評鑑、輿情
- 明確權重（例：財務40% 裁罰30% 評鑑15% 輿情15%），可調
- 總分 = 加權和，能攤開解釋「87分怎麼來的」
- 產出：完整 `kindergartens.csv`

### 模組 L4：裁罰/評鑑/基本資料蒐集
- 從全國教保資訊網、新北市幼兒教育資源網抓裁罰紀錄、評鑑、地址
- 裁罰紀錄當「風險標籤」——用來驗證：高分園是否真的較常被裁罰（殺手鐧論證）
- 地址做 geocoding(Nominatim免費) 轉經緯度給地圖

### 模組 L5：驗證論證（簡報用）
- 做一張圖：風險分數 vs 實際裁罰次數的關聯，證明模型有效
- 這是問答時「你怎麼證明準」的答案

## 四、組員 — 「介面與 AI 呈現」線

你負責把分數變成評審看得到、會驚豔的東西。

### 模組 M1：儀表板骨架（讀假CSV先做）
- 技術建議：前端用 Streamlit(最快) 或 React+FastAPI(較炫)
- 首頁：全部幼兒園風險排名表，可排序、可篩選（公校/非營利、高/中/低）
- 讀 `kindergartens.csv` 呈現，不碰資料抽取

### 模組 M2：單園詳情頁
- 點一間園 → 攤開：總分 + 四個分項雷達圖 + 各項指標數值
- 雷達圖是「可解釋白盒子」的視覺證據，評審一看就懂

### 模組 M3：風險地圖（你的加分亮點）
- Leaflet + OpenStreetMap（免費、不用金鑰、不違反比賽規範）
- 各園依 lat/lng 標點，紅/黃/綠代表風險高中低
- 點擊 popup 顯示：園名、風險分、主要問題
- 可加「規劃稽查路線」的視覺（高風險園連線）當亮點

### 模組 M4：AI 稽查建議報告（Bedrock）
- 串 AWS Bedrock (Claude)，輸入某園的指標數字，生成白話稽查建議
- 例：「風險偏高82分，財務數字分布異常疑似調帳，人事費暴增45%與幼兒數不符，建議優先稽查人事採購憑證」
- 產出寫回 `ai_report` 欄位或即時呼叫
- 卡住備案：Bedrock沒設好，先用預寫好的範本文字，Demo照樣能跑

### 模組 M5：NLP 輿情分析（小樣本亮點）
- 抓少量幼兒園相關網路評論/新聞，用Bedrock做情緒分析
- 產出輿情負面度 → 併入 score_sentiment
- 範圍要小，做1-2間展示即可，別花太多時間

### 模組 M6：Live Demo 部署 + 錄影
- Demo部署網址、錄製操作影片（交件要求項目）
- 部署細節見第六節（最後處理）

## 六、AWS 雲端部署（最後再用，先記著）

先在本機/localhost 把所有功能跑出來，最後 6 小時再上雲。主要由隊長最後處理。

建議最小 AWS 架構：
- **S3**：存原始PDF與處理後CSV
- **Bedrock**：生成稽查建議 + 非營利園掃描財報多模態抽取
- **Textract**（選用）：非營利園表格OCR量產方案（架構圖寫上，展現可行性）
- **前端部署**：Streamlit → EC2 或 App Runner；React → S3靜態網站 + CloudFront；或用 Amplify
- **憑證管理**：一律走 .env + os.environ，push前跑 check_secrets.py

部署順序：先確定本機能跑 → 打包 → 上傳S3/部署前端 → 接Bedrock → 拿到公開Demo網址 → 錄影。
備案：若上雲卡關，用本機 + ngrok 或錄好的影片當Demo，先確保有東西可交。

## 八、風險與備案（先想好才不會慌）
- **OCR來不及**：非營利園只做Bedrock抽1-2份展示，主力用公校決算(有文字層)
- **Bedrock沒設好**：AI報告先用範本文字，架構圖照樣講
- **上雲卡關**：本機Demo + 錄影，先確保有交件
- **資料抽取難**：手動補少數園數字，先求15-20間能完整跑
- **核心原則**：任何時候都要有「能跑的版本」，寧可功能少但完整，不要功能多但跑不動（完成度20%）
